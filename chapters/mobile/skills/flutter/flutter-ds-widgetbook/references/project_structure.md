# Project Structure — File Detection and Location

Before generating a use case, detect which structure the project uses
so the file is placed in the correct spot.

The Widgetbook has **two sections**: UI System (components) and Features (screens).
Both coexist under `widgetbook_[appname]/lib/`.

---

## Step 1 — Detect the structure

Look for the existing folders under `widgetbook_[appname]/lib/`:

### 1a. Look for `ui_system/` and `features/`

If `widgetbook_[appname]/lib/ui_system/` and `widgetbook_[appname]/lib/features/` already exist → the structure is already correct. Continue to step 2.

### 1b. If they do NOT exist — detect a legacy structure and migrate

If `widgetbook_[appname]/lib/` has component folders directly at the root (`atoms/`, `molecules/`, `organisms/`, `components/`), that is a **legacy structure**. Create `ui_system/` and move everything into it:

```
# Legacy (before)                     # Correct (now)
widgetbook_[appname]/lib/             widgetbook_[appname]/lib/
├── atoms/          ───────────→      ├── ui_system/
├── molecules/                       │   ├── atoms/
└── organisms/                       │   ├── molecules/
                                      │   └── organisms/
                                      ├── features/
                                      └── shared/
```

### 1c. If NOTHING exists — create the structure from scratch

**Mandatory action:** Create these folders before generating any use case:

```bash
# Always create these two root folders
mkdir -p widgetbook_[appname]/lib/ui_system
mkdir -p widgetbook_[appname]/lib/features
mkdir -p widgetbook_[appname]/lib/shared
```

Then, according to the main project's style:

### Structure A — Atomic Design + Features
Indicators in the main project: `atoms/`, `molecules/`, `organisms/` folders or Atomic Design naming

```bash
mkdir -p widgetbook_[appname]/lib/ui_system/atoms
mkdir -p widgetbook_[appname]/lib/ui_system/molecules
mkdir -p widgetbook_[appname]/lib/ui_system/organisms
mkdir -p widgetbook_[appname]/lib/ui_system/templates
```

Result:
```
widgetbook_[appname]/lib/
├── main.dart               ← Entry point
├── main.directories.g.dart ← Generated by build_runner
├── ui_system/              ← Design System components
│   ├── atoms/
│   │   ├── button/
│   │   └── text_field/
│   ├── molecules/
│   │   ├── card/
│   │   └── list_tile/
│   └── organisms/
│       └── checkout_form/
├── features/               ← Screens
│   ├── auth/
│   │   ├── login_screen/
│   │   └── register_screen/
│   ├── home/
│   │   └── home_screen/
│   └── profile/
│       └── profile_screen/
└── shared/
```

### Structure B — By components + Features
Indicators in the main project: `components/` or `widgets/` folder, or no Atomic Design

```bash
mkdir -p widgetbook_[appname]/lib/ui_system/components
```

Result:
```
widgetbook_[appname]/lib/
├── main.dart               ← Entry point
├── main.directories.g.dart ← Generated by build_runner
├── ui_system/              ← Design System components
│   └── components/
│       ├── buttons/
│       ├── cards/
│       └── forms/
├── features/               ← Screens
│   ├── auth/
│   ├── home/
│   └── profile/
└── shared/
```

> **Rule:** Never place component use cases directly under `widgetbook_[appname]/lib/`. Always inside `ui_system/`.
> **Rule:** Never place screen use cases outside `features/`. Always inside `features/`.

## Step 2 — Determine whether it's a component or a screen

| The user asks to catalog... | Section | Location |
|---|---|---|
| Button, card, input, badge, icon, etc. | UI System | `lib/ui_system/[atoms\|molecules\|organisms\|components]/` |
| Login, home, detail, checkout, profile, etc. | Features | `lib/features/[feature]/[screen]/` |

If it's a **screen**, follow `references/features_guide.md` for the full process.
If it's a **component**, continue with step 3.

---

## Step 3 — Classify the component (Atomic Design only)

| Category | Criterion | Examples |
|---|---|---|
| **Atom** | Widget with no composable children, the minimal UI unit | `PrimaryButton`, `AppTextField`, `StatusBadge`, `AppIcon` |
| **Molecule** | Composition of 2-4 atoms with a specific function | `SearchBar`, `ProductCard`, `UserAvatar`, `FormField` |
| **Organism** | Complex section with multiple molecules | `CheckoutForm`, `ProductList`, `NavigationBar`, `LoginForm` |
| **Template** | Screen layout without real data | `DashboardTemplate`, `DetailTemplate` |

**Rule of thumb:** if a widget accepts arbitrary child widgets (`child`, `children`)
and has no business logic, it is probably a Molecule or higher.

---

## Step 4 — File name and location

### For components (UI System)
```
widgetbook/lib/
└── ui_system/
    └── [atoms|molecules|organisms|components]/
        └── [name_in_snake_case]/
            └── [name_in_snake_case].use_case.dart
```

| Widget | Category | File path |
|---|---|---|
| `PrimaryButton` | Atom | `ui_system/atoms/primary_button/primary_button.use_case.dart` |
| `ProductCard` | Molecule | `ui_system/molecules/product_card/product_card.use_case.dart` |
| `CheckoutForm` | Organism | `ui_system/organisms/checkout_form/checkout_form.use_case.dart` |
| `CustomSlider` | Atom | `ui_system/atoms/custom_slider/custom_slider.use_case.dart` |

### For screens (Features)
```
widgetbook/lib/
└── features/
    └── [feature_name]/
        └── [screen_name_snake_case]/
            └── [screen_name_snake_case].use_case.dart
```

| Screen | Feature | File path |
|---|---|---|
| `LoginScreen` | auth | `features/auth/login_screen/login_screen.use_case.dart` |
| `HomeScreen` | home | `features/home/home_screen/home_screen.use_case.dart` |
| `ProductDetailScreen` | catalog | `features/catalog/product_detail_screen/product_detail_screen.use_case.dart` |
| `ProfileScreen` | profile | `features/profile/profile_screen/profile_screen.use_case.dart` |

---

## Step 5 — Register in widgetbook.dart (if applicable)

If the project does not use `build_runner` to generate the tree automatically,
remember to add the new use case to the corresponding `WidgetbookComponent`
in the main Widgetbook file.

If it uses `@App` with `build_runner`, the file is detected automatically.

## Project setup (reference)

### pubspec.yaml — required dependencies
```yaml
dependencies:
  widgetbook: ^3.22.0

dev_dependencies:
  widgetbook_annotation: ^3.11.0
  widgetbook_generator: ^3.22.0
  build_runner: ^2.4.0
```

### widgetbook_[appname]/lib/main.dart — entry point
```dart
import 'package:flutter/material.dart';
import 'package:widgetbook/widgetbook.dart';
import 'package:widgetbook_annotation/widgetbook_annotation.dart';

import 'main.directories.g.dart';
import 'shared/code_preview_addon.dart';

void main() => runApp(const WidgetbookApp());

@App()
class WidgetbookApp extends StatelessWidget {
  const WidgetbookApp({super.key});

  @override
  Widget build(BuildContext context) {
    return Widgetbook.material(
      directories: directories,  // generated by build_runner
      addons: [
        const CodePreviewAddon(),  // must be first in the list
        MaterialThemeAddon(
          themes: [
            WidgetbookTheme(name: 'Light', data: AppTheme.light),
            WidgetbookTheme(name: 'Dark', data: AppTheme.dark),
          ],
          initialTheme: WidgetbookTheme(name: 'Light', data: AppTheme.light),
        ),
        TextScaleAddon(min: 1.0, max: 2.0),
        LocalizationAddon(
          locales: AppLocalizations.supportedLocales,
          localizationsDelegates: AppLocalizations.localizationsDelegates,
        ),
        DeviceFrameAddon(devices: [
          Devices.ios.iPhone13,
          Devices.ios.iPadPro11Inches,
          Devices.android.samsungGalaxyS20,
        ]),
      ],
    );
  }
}
```

### Command to regenerate the tree after adding use cases
```bash
dart run build_runner build --delete-conflicting-outputs
```

## shared/ folder — catalog widgets

Create `widgetbook_[appname]/lib/shared/` for reusable widgets within the Widgetbook itself:

```
widgetbook_[appname]/lib/shared/
├── code_preview_addon.dart  ← Code preview addon (mandatory, create only once)
├── mock_providers.dart      ← Provider wrappers to isolate screens
└── mock_data.dart           ← Mock data shared across use cases
```

Import it in each use case that needs it:
```dart
// From ui_system/atoms/button/ → 3 levels up
import '../../../shared/code_preview_addon.dart';
import '../../../shared/mock_data.dart';

// From features/auth/login_screen/ → 3 levels up
import '../../../shared/code_preview_addon.dart';
import '../../../shared/mock_providers.dart';
```
